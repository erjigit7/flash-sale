## 2026-10-02 10:14:01 +0600 — план согласован

(Это первая отметка `date` после утверждения. Сам момент утверждения лежит между 09:55:57 и 10:14:01, точнее его не снимали.)

План лежит в [docs/PLAN.md](docs/PLAN.md). Ключевые решения:

- **Атомарный резерв**. Один SQL-оператор `UPDATE sales SET available = available - qty WHERE available >= qty AND starts_at <= now() AND ends_at > now()`, в том же операторе (CTE) `INSERT` позиции корзины. Почему: при read-check-write два покупателя могут одновременно прочитать «осталось 1». CHECK `available >= 0` стоит последним рубежом.
- **Время по часам БД (`now()`)**. Одна точка истины, браузер только рисует таймер.
- **Идемпотентный checkout**. Ключ `Idempotency-Key`, `unique(user_id, idempotency_key)` и `unique(reservation_id)`. Переход `ACTIVE→CHECKOUT` условный, поэтому выполняется один раз.
- **Зависшая оплата**. Позиция в статусе `CHECKOUT`, expirer её не трогает, товар держится. Результат приходит через webhook, а reconciler страхует опросом заглушки. Обе ветки сходятся в одну идемпотентную функцию.
- **Письма через outbox**. Запись создаётся в той же транзакции, что и смена статуса, `unique(dedup_key)`, одно письмо на заказ.
- **Заглушка оплаты — отдельный контейнер**, так она ведёт себя как внешний провайдер (сеть, асинхронный webhook, «зависание»).

Решения:
- **Nest 12 вместо Nest 11, ESM + Vitest вместо Jest.** Актуальный Nest 12.1 опубликован только как ESM (`"type": "module"`). Его официальный шаблон `nest new` по умолчанию генерирует ESM-проект с Vitest. Jest с ESM работает только через `--experimental-vm-modules`, поэтому берём штатный путь. Это отступление от плана (там был Jest), сделанное осознанно. Заодно Prisma 7 с генератором `prisma-client` (ESM) ложится на ESM-проект без конфликтов, и откат на Prisma 6 пока не нужен.
- **TypeScript 6.0, а не 7.0.** TS 7 уже стал `latest`, но ts-jest требует `<7`, а Nest CLI 12 сам тянет `~6.0.2`. Берём 6.0, чтобы весь тулчейн был согласован.
- **Prisma 7.10.0, а не `latest`.** Тег `latest` у пакета `prisma` сейчас указывает на `8.0.0-rc.19`, то есть на релиз-кандидат. Берём последний стабильный 7.10.0, той же версии, что `@prisma/client`. npm 11 требует явно разрешить install-скрипты (`allowScripts` в package.json), иначе движок миграций не скачается.
- **Каждый сервис — отдельный npm-пакет со своим lock-файлом, без npm workspaces.** Это отступление от плана: так у каждого Dockerfile контекст сборки сводится к своей папке, и не нужно тащить корневой lock. Корневой `package.json` содержит только удобные скрипты (`npm run up`, `npm test`).
- **Заглушка оплаты на Fastify, TypeScript исполняет сам Node 24** (type stripping, `erasableSyntaxOnly`). Сборка и транспилятор не нужны, и сервис остаётся минимальным.
- **Фронт в compose отдаёт nginx.** Он проксирует `/api` и `/socket.io` с поддержкой WebSocket upgrade, а в Vite dev-сервере такой же прокси. Получается один origin и никакого CORS.
- **Образы на `node:24-slim` (Debian), не alpine.** Движку миграций Prisma нужен openssl, на slim это ставится без сюрпризов с musl.

## 2026-10-02 10:30:42 +0600 — этап 2: схема БД, миграция, идемпотентный seed

Сделано:
- Prisma-схема: `users`, `sales`, `reservations` (позиции корзины), `orders`, `email_outbox`, `notifications`, enum'ы статусов. Адрес БД задаётся в `prisma.config.ts`, как требует Prisma 7, с дефолтом на postgres из compose.
- В миграцию вручную добавлено то, что Prisma не выражает:
  - CHECK `0 <= available <= total_qty`, `available + withdrawn_qty <= total_qty`, `ends_at > starts_at` и другие;
  - **частичный уникальный индекс** `(user_id, sale_id) WHERE status IN ('ACTIVE','CHECKOUT')`: одна «живая» позиция на покупателя в распродаже.
- id генерирует БД (`gen_random_uuid()`), а не Prisma на клиенте. Причина: критичные вставки идут сырым SQL (резерв одним CTE), и там id должен проставляться сам.
- Seed идемпотентный (поправка 3):
  - аккаунт магазина делается upsert по email;
  - три демо-распродажи создаются через `INSERT ... ON CONFLICT (slug) DO NOTHING`, время старта и конца считается от `now()` БД.
  - Проверено: первый запуск создаёт 3, повторные 0. После `down -v` всё создаётся с нуля.
- Контейнер бэкенда при старте выполняет `prisma migrate deploy` → seed → `exec node dist/main.js`. `exec` нужен, чтобы SIGTERM доходил до node: с обёрткой npm при рестарте сыпалась ошибка.
- Защита e2e: globalSetup откажется запускаться, если имя БД не оканчивается на `_test`. Тесты чистят таблицы и не должны случайно снести демо-данные. Проверено, что на `flashsale` тесты падают с понятной ошибкой.
- `/api/health` теперь проверяет и соединение с БД.

Решения:
- Метки времени `timestamptz(3)` (миллисекунды): совпадает с точностью JS Date, и в API не возникает расхождений округления.
- `version` у распродажи сделан `Int`, а не `BigInt`: BigInt не сериализуется в JSON, а 2^31 изменений остатка для одной распродажи с запасом.
- `slug` у распродажи нужен только для идемпотентного seed. У распродаж, созданных в UI, он null, и unique ему не мешает.

## 2026-10-02 10:39:20 +0600 — этап 5: корзина — атомарный резерв, освобождение, истечение удержания

Сделано:
- **Резерв одним SQL-оператором** (CTE): `UPDATE sales SET available = available - qty WHERE available >= qty AND qty <= max_per_order AND starts_at <= now() AND ends_at > now()` и в том же операторе `INSERT` позиции корзины.
  - Если покупатель уже держит товар этой распродажи, частичный уникальный индекс роняет INSERT, и весь оператор откатывается вместе со списанием.
  - Причину отказа (`not_started`, `sale_ended`, `sold_out`, `insufficient_stock {available}`, `qty_over_limit`, `already_in_cart`) определяет отдельный read-only запрос, только для понятного ответа.
- **Просят больше, чем осталось**: отказ целиком, клиенту возвращается текущий остаток (договорённость).
- **Освобождение позиции** (`DELETE /api/reservations/:id`) и **истечение удержания** (`expireDue`, воркер раз в секунду) делят одну SQL-часть: перевести позиции из ACTIVE и вернуть остаток одним UPDATE на распродажу. Если распродажа уже закончилась, остаток уходит не на витрину, а в `withdrawn_qty`.
- Expirer берёт только `ACTIVE` через `FOR UPDATE SKIP LOCKED`. Позиции в `CHECKOUT` (оплата начата) не трогает, это основа пунктов «оплата завершается после истечения» и «зависшая оплата держит товар». Позиции завершившихся распродаж тоже не трогает: их отменяет уборка после окончания с уведомлением владельцу (этап 10).
- **Шина доменных событий** (`DomainEvents`): сервисы публикуют `stock.changed` с монотонной `version` и `reservation.changed` строго после commit. Socket.IO подпишется на этапе 6.
- Тестовое приложение слушает настоящий порт: supertest больше не поднимает сервер на каждый запрос, и тот же порт понадобится для webhook'ов от заглушки.

Тесты (всего 25, все зелёные):
- **гонка**: 1 единица и 50 параллельных покупателей → ровно 1 позиция, 49 `sold_out`. 10 единиц и 100 покупателей → ровно 10. Один покупатель жмёт 10 раз параллельно → одна позиция, списание одно. 3 при остатке 2 → отказ, остаток 2.
- **окно**: до старта `not_started`, после «наступления старта» (сдвиг окна относительно `now()` БД) покупка проходит. После конца `sale_ended`.
- **удержание**: TTL ровно 600 с по часам БД. После истечения товар вернулся, событие с новой версией опубликовано, товар достаётся другому. Три параллельных запуска воркера возвращают товар один раз.
- **инвариант** `total = available + ACTIVE + CHECKOUT + PURCHASED + withdrawn` проверяется после гонок.

**Мутационная проверка теста гонки.** Временно заменил атомарный SQL на наивный «прочитал → проверил → записал».
- Результат: **1 единицу «продали» всем 50 покупателям, 10 единиц всем 100**.
- Тест это поймал (`expected length 1 but got 50`). Мутацию откатил, тест снова зелёный.
- Значит, тест реально ловит перепродажу, а не проходит случайно.

## 2026-10-02 10:41:57 +0600 — этап 6: realtime (Socket.IO)

Сделано:
- `RealtimeGateway` сам ничего не решает, он только пересылает доменные события (опубликованные после commit) в комнаты:
  - `showcase`: все подключённые, в том числе без входа. События `sale:stock`, `sale:started`, `sale:ended`.

- Проверено в контейнерах: WebSocket проходит через nginx фронта (`:8080/socket.io`, transport=websocket).

Тесты (всего 29, все зелёные):
- **две вкладки и анонимный зритель**: покупка в одной вкладке → все трое получают `sale:stock` с новым остатком и версией. Истечение удержания → обе вкладки видят возврат. Личное событие корзины приходит только владельцу.
- **10 параллельных покупок**: 10 событий с уникальными версиями, событие с максимальной версией несёт итоговый остаток. Клиент может отбрасывать устаревшие события.
- **старт**: обе вкладки получают `sale:started`, и к этому моменту БД уже пускает в покупку (`starts_at <= now()`).
- **`time:ping`** отдаёт время БД.

Решения:
- Остатки рассылаются всем в комнате `showcase`, а не по комнатам `sale:{id}`, как было в плане. Витрина показывает все распродажи сразу, распродаж единицы, и подписка по каждой только усложнила бы клиент. При росте нагрузки перейдём на комнаты по распродажам и Redis-адаптер (записано в «что дальше»).
- Сигнал `sale:started` нужен только для UI. Купить до старта нельзя независимо от него, это проверяет атомарный SQL. Кнопка на клиенте откроется по синхронизированному таймеру или по этому сигналу, смотря что придёт раньше.

## 2026-10-02 10:44:48 +0600 — этап 7: заглушка платёжного провайдера

Сделано (`payment-stub/`, Fastify, отдельный контейнер):
- `POST /payments {idempotencyKey, amountCents, scenario, callbackUrl}` отвечает **202 «в обработке»**, а результат присылает позже webhook'ом, как настоящий провайдер.
  - Сценарии: `SUCCESS` и `DECLINE` отвечают через ~1,5 с. `HANG` молчит, пока платёж не разрешат вручную.
- **Идемпотентность по ключу**: тот же ключ возвращает тот же платёж (`idempotentReplay: true`), второго списания нет. Тот же ключ с другой суммой даёт 422, а не новый платёж.
- **Webhook подписан HMAC-SHA256** (`x-signature: sha256=...`) и доставляется **at-least-once**: повторы с экспоненциальной паузой до ответа 2xx. Значит, бэкенд обязан обрабатывать повторную доставку идемпотентно, и это будет проверено тестом.
- `POST /payments/:id/resolve` разрешает зависший платёж ровно один раз, повтор даёт 409 `already_resolved`. `POST /payments/:id/redeliver` повторно шлёт тот же результат, это демонстрация дублей.
- HTML-панель на http://localhost:4000: список платежей, кнопки «Подтвердить» и «Отклонить» для зависших, «Повторить webhook». Обновляется сама.
- Проверено руками (curl и браузер): повторный POST с тем же ключом, ключ с другой суммой, двойное разрешение, повторы webhook, кнопка «Отклонить» в панели.

Решения:
- Хранилище в памяти. Для заглушки этого хватает. При рестарте контейнера висящие платежи теряются, и бэкенд это переживает: reconciler на 404 переотправит платёж с тем же ключом. Записано как известное ограничение.
- Сценарий выбирает покупатель при оплате, это аналог тестовых карт у Stripe. Передаётся полем `scenario`.
- Найдена и исправлена мелочь в панели: перерисовка каждые 1,5 с меняла кнопки прямо под курсором. Теперь перерисовка идёт только при изменении данных.

  - `INSERT` заказа с `ON CONFLICT (user_id, idempotency_key) DO NOTHING`.
  
  Второй параллельный запрос ждёт блокировку строки, перепроверяет условие, получает 0 строк и возвращает уже созданный заказ (200, `replay`). Тот же ключ для другой позиции даёт 422, и переход в CHECKOUT откатывается. После истечения удержания checkout отвечает 410 `hold_expired`.
- **Отправка в платёжку после commit** работает как outbox: заказ `PENDING` без `provider_payment_id`.
  - Сразу после checkout заказ отправляется асинхронно, ответ клиенту не ждёт платёжку.
  - Воркер повторяет отправку с экспоненциальной паузой. Захват идёт через `FOR UPDATE SKIP LOCKED` со сдвигом `next_attempt_at` (аренда).
  - Ключ у провайдера равен `order.id`, поэтому повторная отправка не создаёт второго платежа.
- **Webhook** `POST /api/payments/webhook`: HMAC-SHA256 по сырому телу (`rawBody: true`) и `timingSafeEqual`. Без подписи или с чужой подписью ответ 401.
- **`applyPaymentResult`**, одна идемпотентная функция для webhook и reconciler. Условный `PENDING → PAID/FAILED`, повтор получает 0 строк и ничего не меняет. В той же транзакции:
  - PAID: позиция `→ PURCHASED`;
  - FAILED: позиция `→ RELEASED` и возврат остатка;
  - запись письма в outbox с `dedup_key = 'order:<id>'`, одно письмо на заказ. Отправитель появится на этапе 9.
- **Reconciler** раз в 5 с опрашивает платёжку по PENDING-заказам: это страховка от потерянного webhook. Если провайдер «не знает» платёж (заглушка перезапустилась), `provider_payment_id` сбрасывается, и заказ уходит заново с тем же ключом.

## 2026-10-02 10:56:04 +0600 — этап 10: окончание распродажи

Сделано:
- `SaleFinalizer.finalizeEnded()`, воркер раз в секунду. На одну распродажу приходится **один SQL-оператор** (цепочка data-modifying CTE), поэтому всё атомарно:
  - распродажа захватывается `FOR UPDATE SKIP LOCKED` по условию `ends_at <= now() AND (finalized_at IS NULL OR available > 0)`;
  - позиции `ACTIVE → CANCELLED`, их количество уходит в `withdrawn_qty`, а не на витрину;
  - каждому владельцу уведомление в кабинет (`notifications`) и письмо (outbox), оба с `dedup_key = 'sale-ended:<reservationId>'`, то есть ровно один раз;
  - остаток витрины уходит в `withdrawn_qty`, `available = 0`, ставится `finalized_at`.
- **Позиции в `CHECKOUT` не трогаются**: оплата, начатая до конца, досчитывается. При успехе товар продан, при отказе уходит в «снято», а не на витрину. Возврат остатка везде идёт через `CASE WHEN ends_at > now()`.
- Expirer не трогает позиции завершившихся распродаж. Поэтому удержание, которое истекло уже после окончания, отменяется уборкой с уведомлением, а не «возвращается» на витрину.
- После commit идут события `stock.changed`, `reservation.changed (CANCELLED)` и `notification` в сокет владельца.
- `GET /api/notifications` и `POST /api/notifications/read-all` для кабинета.

Тесты (5 новых, всего 52, все зелёные). Сценарий: 5 единиц; A держит в корзине, B начал оплату (HANG), C купил, 2 лежат на витрине. Распродажа закончилась →

- A получил сокет-уведомление и запись в кабинете. Повторный запуск уборки ничего не меняет. **В Mailpit ровно одно письмо A**, у B и C писем об окончании нет;
- оплата B досчитывается после окончания. Успех → продано 2. Отказ → снято 4, на витрину товар не вернулся;
- удержание, истёкшее после окончания, товар не «воскрешает».

## 2026-10-02 11:50:01 +0600 — заглушка хранит платежи на диске (по находке заказчика №1)

Что и почему [решение: заказчик]: платёж, принятый провайдером, должен пережить рестарт провайдера.

Как сделано [решение: агент]:
- **Json-файл в volume `stubdata:/data`, а не таблица в нашей Postgres.** У внешнего провайдера своё хранилище: если бы заглушка писала в БД магазина, она перестала бы вести себя как внешний сервис.
- **Платёж записывается на диск до ответа «202 принят».** Если записать не удалось, платёж откатывается в памяти и клиент получает 500, то есть «не принят». Запись атомарная: временный файл, затем `rename`. При падении посреди записи на диске остаётся прежняя целая версия.
- **Восстановление при старте**: HANG продолжает висеть (тот же платёж ждёт решения в панели), таймеры SUCCESS и DECLINE досчитываются по оставшемуся времени, недоставленные webhook отправляются снова (получатель идемпотентен). Состояние доставки webhook сохраняется после каждой попытки.
- **Окно хранения**: завершённые платежи и их ключи идемпотентности живут 24 часа (`RETENTION_HOURS`), как у Stripe. Висящие не удаляются никогда.
- **В бэкенде** ветка reconciler «провайдер ответил 404» остаётся как защитная, комментарий поправлен: в норме туда больше не попадаем.
