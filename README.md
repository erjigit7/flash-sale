# Флэш-распродажа

Тестовое задание MadDevs (Agentic Developer), задание 4. Сервис ограниченных распродаж: товара меньше, чем покупателей, продажа открывается в момент старта, остатки меняются у всех в реальном времени, товар удерживается в корзине, оплата идёт через заглушку, которая может подтвердить, отклонить или «зависнуть».

## Запуск

Нужны только **Docker Desktop (Compose v2)** и свободные порты 8080, 3000, 4000, 8025, 1025, 5432. Ни Node, ни `.env` не нужны.

```bash
git clone https://github.com/erjigit7/flash-sale
cd flash-sale
docker compose up --build
```

Первый запуск собирает образы (около минуты), миграции и демо-данные применяются сами. Повторный запуск данные не дублирует.

| Что | Адрес |
|---|---|
| Приложение | http://localhost:8080 |
| Экран магазина | http://localhost:8080/shop, пароль `shop` |
| Панель заглушки оплаты | http://localhost:4000 |
| Письма (Mailpit) | http://localhost:8025 |

Покупатель входит по email без пароля (демо-вход). Сессия хранится в `sessionStorage`, поэтому **каждая новая вкладка может быть отдельным покупателем**. Открывайте вторую вкладку заново, а не дублированием: дубль копирует сессию.

Сбросить всё: `docker compose down -v`. Для быстрого демо удержания: `HOLD_TTL_SECONDS=60 docker compose up --build`.

## Как попробовать

1. Войдите на `/shop`, нажмите «Выставить на распродажу» (старт через минуту, 1 штука).
2. В двух вкладках войдите двумя разными email. До старта кнопка закрыта, в момент старта открывается у обеих.
3. Обе жмут «В корзину»: одна получит товар, у второй «Закончилось». Остаток обновился без перезагрузки.
4. В корзине выберите сценарий оплаты: «пройдёт», «отклонить» или «зависнуть». При «зависнуть» решение принимается в панели заглушки (:4000).

## Что внутри

- **backend**: NestJS 12 + Prisma 7 + PostgreSQL 18, REST под `/api`, Socket.IO, фоновые воркеры в том же процессе.
- **frontend**: React + Vite + TypeScript, TanStack Query; отдаётся nginx, который проксирует `/api` и `/socket.io` (один origin, CORS не нужен).
- **payment-stub**: отдельный сервис (Fastify) со своим хранилищем на диске, подписанными webhook'ами и HTML-панелью.
- **Mailpit** для писем.

## Как закрыто «ожидаемое поведение»

| Требование | Как |
|---|---|
| Последнюю единицу двоим не продать | Один SQL `UPDATE … WHERE available >= qty` и вставка позиции корзины в одном операторе, плюс CHECK `available >= 0` |
| До старта купить нельзя | Проверка `starts_at <= now()` внутри того же SQL, поэтому запрос в обход кнопки тоже отклоняется |
| Все время по серверу | Решения принимает `now()` БД; браузер лишь показывает таймеры по серверному времени (поправка как в NTP) |
| Остатки без обновления страницы | Socket.IO, события с монотонной `version`, старые события клиент отбрасывает |
| Удержание 10 минут, возврат на витрину | Воркер раз в секунду возвращает остаток и шлёт событие; позиции в оплате он не трогает |
| Оплата, начатая до истечения, завершается | Позиция в статусе «в оплате» не истекает |
| Заглушка «зависла» | Заказ ждёт, товар держится; результат придёт webhook'ом (HMAC) или его подберёт reconciler, опрашивающий заглушку |
| Двойной клик «оплатить» | `Idempotency-Key` + уникальные индексы + условный переход позиции; у провайдера ключ равен id заказа |
| Одно письмо | Outbox с уникальным `dedup_key`, запись создаётся в транзакции события |
| Конец распродажи | Один SQL на распродажу: непроданное снимается, корзины отменяются, владельцам уведомление и письмо, по одному разу |

## Тесты

```bash
npm test             # 61 бэкенд-тест в контейнере: настоящий Postgres, заглушка, Mailpit
npm run test:e2e     # 9 браузерных тестов Playwright на отдельном стеке (удержание 15 с)
node scripts/check-restarts.mjs   # рестарты вживую при поднятом стеке
```

Бэкенд-тесты не ждут таймеров: время двигается в БД, воркеры вызываются напрямую. Среди них гонка за последнюю единицу (50 покупателей на 1 штуку, 100 на 10), двойная оплата, истечение удержания, зависшая оплата и оплата после истечения, дубли webhook, одно письмо (проверка через API Mailpit), конец распродажи и хаос-тест на 30 покупателей с проверкой учёта до единицы. Тест гонки проверен мутацией: с наивным «прочитал → проверил → записал» он падает.

## Состояние проекта

**Работает**: всё из задания, подтверждено тестами выше и ручной проверкой заказчика. Рестарты бэкенда и заглушки во время зависшей оплаты не теряют заказ и не создают второй платёж.

**Осознанные решения и ограничения**
- **Зависшая навсегда оплата держит товар бесконечно.** Так требует задание: заказ не должен ни вернуть товар, ни продать его дважды, пока платёжка не ответила. Альтернативы (жёсткий таймаут, ручная отмена магазином) в объём не вошли.
- **После отказа оплаты повторно оплатить ту же позицию нельзя**, товар возвращается на витрину, и его кладут в корзину заново. Решение заказчика: одна позиция даёт не больше одного заказа, модель проще и безопаснее. Цена: между отказом и новой корзиной другой покупатель может успеть взять товар.
- **Письмо «ровно одно»** гарантировано на уровне БД. Узкое окно остаётся: если процесс упадёт между ответом почтового сервера и записью «отправлено», письмо уйдёт повторно (exactly-once поверх SMTP невозможен). Смягчает постоянный Message-ID.
- **Вход без пароля** и пароль магазина из переменной окружения только для демо.
- **Один экземпляр бэкенда.** Воркеры написаны безопасно для нескольких (`SKIP LOCKED`), но рассылка Socket.IO между экземплярами требует Redis-адаптера, его нет.
- Заглушка хранит платежи в JSON-файле; завершённые удаляются через 24 часа.
- Мобильную вёрстку и обрыв связи в браузере автотестами не покрывали, проверял заказчик вручную.
